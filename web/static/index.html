Someone says “it’s broken” and posts a picture.

No stack trace. No file names. SnapLocate reads the pixels with Gemma 4, finds those exact strings in the repo, and walks Graphify’s call graph outward — returning the likely source files, the call path, an S/M/L difficulty and the blast radius.

Running the pipeline

Screenshot

What Gemma 4 saw. Each box is a word it read off the screen — click one to see which files contain that exact text.

On-screen strings click to highlight files

The strings being searched for. Suspect means the model thinks it came from the broken code path.

Code graph

How these files connect in the real code. Colour = community (a subsystem); an orange line means one file calls the other.

Files

Where to start looking. search = the text was found here; graph = it sits near files that matched.

Assessment

S small, M medium, L large — from how many subsystems the fix touches. Thresholds are untuned.

Blast radius

What a change here could affect. An upper bound, not a prediction of the diff.

Run detail

SnapLocate — Python standard library only. No pip install at runtime, no npm, no build step, no CDN: it renders with the wifi dead. Ranking weights are untuned hand-picked values; any accuracy figure comes from a small hand-built issue set and is not comparable to MM-IssueLoc, SWE-bench M or any published benchmark. The bounding-box convention is read from the API at runtime, never hard-coded here. A result replayed from cache is always labelled as a replay, and a fallback graph is never presented as Graphify.
